# 决策结构、对线与位置分工，以及 LLM 介入点设计

后续实施以[LLM 战略增强实施与审计计划](LLM_STRATEGY_IMPLEMENTATION_PLAN_ZH.md)为准；其中按用户要求进一步收窄了微操改动范围。

日期：2026-09-21。基于 `cb814c6c8dc51ed08045d6efd9f4a48147992711` 的代码继续分析。配套阅读：[总体架构与网络接入方案](AI_DECISION_ANALYSIS_ZH.md)。本文描述已检查的代表性代码及建议设计；没有对局测试，没有修改 Bot 行为。

## 1. 把现在的脚本画成“决策树”

项目没有一棵统一的决策树。更接近下面三条并行链路：

```text
选人阶段
└─ 英雄选择、position 1–5、分路、对应加点与出装模板

正常对局
├─ 行为模式竞争：各自返回 GetDesire，争取成为当前模式
│  ├─ laning：继续对线是否值得？是否有可补的小兵？
│  ├─ attack / roam / team_roam：交战、跟随、特殊目标等
│  ├─ retreat：血量、人数、敌塔、特殊单位等是否要求撤退？
│  ├─ defend：是否该回去守塔／基地？
│  ├─ push：哪一路具备推塔条件？
│  ├─ roshan：人数、输出、生存和局势是否允许？
│  ├─ farm：是否需要发育，附近资源是否合适？
│  └─ ward / rune / assemble / shop 等专项模式
│      └─ 被选中的模式 Think：目标选择 → 移动／攻击等
├─ 技能、物品即时决策
│  └─ 英雄 SkillsComplement / 通用物品逻辑
│      └─ 检查一组条件 → 按优先顺序施法／用物品
└─ 经济与后勤
   ├─ ItemPurchaseThink：清单 → 合成组件 → 购买
   ├─ 升级、买活、信使
   └─ MinionThink：召唤物／幻象等
```

**上面的树是功能分类，不代表 retreat 永远先于 push、或 attack 永远先于 farm。** 实际由模式分数、提前返回、引擎默认逻辑和当前动作共同决定。不同模块也可能发出互相竞争的动作。

例如 `mode_farm_generic.lua` 自己就包含 `ShouldRun` 分支，危险时返回高意愿并切入逃跑状态。不能认为“当前是 farm 模式”就一定在刷钱，也不能把所有安全逻辑只放在 retreat 适配器中。

这种设计的优点是反应快、英雄知识容易逐条补齐；弱点是多个局部正确的判断未必形成一个连贯团队计划。可能出现“大家都认为该推，但各自选择不同路”或“刚集结，又因其他模式分数波动离开”。这些是架构风险，不是本次已复现的具体对局故障。

## 2. 对线实际做了什么，能否评价强度

### 2.1 对线由三部分叠加

1. `mode_laning_generic.lua`：决定是否保持对线，对部分英雄／组合提供补刀、反补和站位动作。
2. `FunLib/override_generic/mode_laning_generic.lua`：为列入特殊名单的英雄补充替代对线行为。
3. 英雄技能模块及引擎默认行为：技能消耗、击杀机会、反打等不全在对线模式里。

因此不能只读一个 laning 文件就评价全部英雄。下述特性也不能一概推广到所有英雄。

### 2.2 当前源码中可确认的能力

| 能力 | 已检查的实现 | 设计倾向／局限 |
|---|---|---|
| 补刀 | 替代逻辑用 `GetAttackProDelayTime` 和 `WillKillTarget` 预测攻击到达时能否击杀 | 比单纯比较当前血量更细；未证明能完整预测全部弹道和小兵同时伤害 |
| 反补 | 替代逻辑检查己方小兵血量比例、当前生命与攻击力 | 比补刀预测简单，代表性实现不是完整伤害时间轴 |
| 辅助让刀 | 检查核心对线伙伴是否存活且在附近；外层逻辑也有核心附近限制 | 有资源倾斜意识，不是所有人同权抢刀 |
| 普攻压制 | 替代逻辑中，辅助在近处敌兵不多时尝试攻击敌方英雄 | 偏低风险压制；目标筛选相对简单，没有完整换血收益模拟 |
| 技能消耗 | 英雄 `Consider*` 单独判断；如斧王 W 在对线、蓝量比例大于 0.5 等条件下消耗 | 强依赖单英雄代码质量，不是统一的“压制强度”参数 |
| 避免危险 | 替代逻辑检查近期受伤、敌方集火、塔仇恨，调整到较安全位置 | 有保命逻辑，但其优先级还受外层调用影响 |
| 站位 | 根据兵线前沿、敌方最大攻击距离等选位置 | 更像距离规则，不等于模拟每个技能的威胁区 |
| 离开对线 | 时间、等级、团队经济、基地威胁参与评分 | 是阶段阈值，不是完整的对线胜负评估 |

`mode_laning_generic.lua` 的部分普通评分：开局 10 秒内约 0.268；9 分钟内且等级不高于 7 时约 0.446；12 分钟内且等级不高于 11 时约 0.369；随后还有等级／经济判断。**这些数字是参与模式竞争的权重，不是对线实力分数或胜率。** 特殊模式与英雄可能走其他路径。

还要留意调用层次：外层自定义 `Think` 会先尝试补刀／反补，然后才调用替代 `Think`；而调用后外层还可能继续发出站位移动。因此替代文件里的“安全优先”不能直接解释为整条调用链最终的动作优先级。建议记录每帧／决策周期最后提交的动作及来源，再决定是否重构统一动作提交器。

### 2.3 对线强度的谨慎判断

从结构看，项目有实用的补刀、保命、让资源和技能条件规则；更有把握的潜力在**规则明确的局部反应**。更值得增强的是**双人路长期配合、兵线管理、什么时候离线、什么时候换线和求援**。

在本次检查的对线、刷钱和团队游走文件中，没有找到清晰完整的拉野／堆野调度链。这个结论不等于引擎默认行为或其他代码绝对没有相关动作。也不能据此断言实际比某段位玩家强或弱。

建议对线测试拆成：5／10 分钟补刀和反补、经济／经验差、死亡、补给消耗、漏经验时间、辅助误抢关键补刀、核心被单独留在线上的风险，以及相同英雄组合交换边后的结果。FretBots 的数值增益必须固定或关闭，否则无法区分操作／决策提升与属性加成。

## 3. Position 1–5 的当前侧重

`J.IsCore(bot)` 直接定义为 `J.GetPosition(bot) <= 3`。很多公共判断因此只分“核心”和“辅助”；英雄标签（先手、控制、耐久、治疗等）又是另一套维度，不应混同。

| 位置 | 默认分路 | 已见代码偏向 | 不应过度推断的部分 |
|---|---|---|---|
| 1 | 优势路，与 5 配对 | farm 初始化为 `beVeryHighFarmer`；部分转团条件对其更宽容；可优先获得补刀 | 不代表永远不参团，也没有独立完备的四保一计划 |
| 2 | 中路 | `beHighFarmer`；部分人数和团队活动条件满足时压低 farm | 不代表自动计算所有游走时机或稳定掌控符点 |
| 3 | 劣势路，与 4 配对 | `beNormalFarmer`；中期部分条件更倾向响应团队活动 | “先手／肉盾”还取决于英雄标签、装备及技能，不是 position 自动赋予 |
| 4 | 劣势路，与 3 配对 | 归为辅助；插眼、让核心资源、跟随等公共逻辑；部分英雄有专门出装 | 未见全项目统一的“4 必须游走、5 必须留线”规划器 |
| 5 | 优势路，与 1 配对 | 同属辅助；与 1 的分路／让刀关系；部分英雄出装更偏团队功能 | 与 4 的差别主要散在分路和英雄模板，不是两套全面独立的决策系统 |

刷钱并不简单等于 position 排序。`mode_farm_generic.lua` 同时检查团队活动、双方存活、基地防守、Roshan／魔晶相关目标等，并在部分路径使用随时间增长的 farm cap。`aba_site.ts` 还有按英雄和关键装备判断“是否该继续刷”的规则。因此“1 比 2 更偏发育”是倾向，不能当作全局严格排序。

`mode_ward_generic.lua` 对 position ≤ 3 提前返回，表明该模式主要服务 4／5。具体返回值是 `false` 而非数值 0，属于接口一致性检查点；本次没有验证引擎对此的实际处理。

### 具体例子：位置模板的差异并不均匀

- **水晶室女**：`hero_crystal_maiden.lua` 给 4 号位安排骨灰、梅肯、微光、卫士胫甲、魂瓮等路径；5 号位包含战鼓、微光、韧鼓升级、笛子等路径。1／2 则复用其 3 号位模板。这里只转述仓库清单，不把它当成当前版本最优出装推荐。
- **敌法师**：`hero_antimage.lua` 的 2／3／4／5 全部引用 1 号位清单，包含狂战、分身等。把敌法改成 5 号位，并不会因此获得完整的辅助出装。

所以更合理的后续模型是：**position 决定经济优先级，英雄能力决定战术职责，当前局势决定这段时间具体做什么。** 三者联合，不能仅用一个 role 数字判断。

## 4. LLM 应介入哪些点

原则：只把需要跨时间、跨英雄、跨目标权衡的选择交给 LLM。模型选择已经可执行的计划，不直接发送走位／施法动作。每个介入点都要具备输入、候选、执行器、过期条件和回退。

以下频率、阈值均为起始设计，不是已测最优值；“触发”通常只标记需要复核，再合并到队伍级请求，不等于立即多发一次 LLM 调用。

| 介入点 | 主要触发 | LLM 输出的受限选择 | 本地执行与撤销 |
|---|---|---|---|
| 开局分工 | 选人结束／阵容确定 | 当前阵容可行的对线组合、经济优先级、保护对象 | 分路适配器；死亡／持续劣势后复核；第一版不改选人 |
| 对线方针 | 每 60–90 秒；连续死亡；对手换线；关键等级窗口 | `secure_farm / pressure / hold_lane / rotate_support / swap_lane` 候选 | 调整压制预算、伙伴关系和区域；危险时本地撤退 |
| 辅助离线／支援 | 兵线可控、核心可独立、边路击杀窗口 | 哪个辅助支援哪路、集结对象、回线条件 | 4／5 号位任务适配；伙伴危险或目标消失即取消 |
| 地图资源分配 | 丢一塔、被入侵、团战结束；每 45–90 秒复核 | 各核心安全发育区、谁收危险线、谁掩护 | farm／防守区域分配；可见敌情变化立即重算安全性 |
| 团战后转化 | 团战聚合窗口关闭 | 推塔、Roshan、占区、补状态、止损 | 既有 push／roshan／farm 等适配；参与者死亡、无兵线等取消 |
| 推进与高地 | 有盾、兵线到位、关键装备完成、敌方复活临近 | 推哪路、多少人参与、推进终点、停手条件 | 高地计划需更严格校验；本地保命与基地威胁优先 |
| 防守与资源交换 | 敌方集结／塔受压、人数劣势 | 守塔、放塔换边线、回防基地、延迟交战 | 核心基地防守硬规则不得被战略“放塔”覆盖 |
| Roshan／盾节奏 | 击杀、刷新可能、拿盾、盾将消失 | 打盾／控区／推塔／回补；指定合法持盾候选 | 所有权和寿命使用可验证信息；拾取执行仍本地完成 |
| 视野与开雾 | 新团队目标、关键技能就绪、视野缺口 | 候选插眼区域、开雾队伍、路线、目标区 | 需要新建路线／任务适配器；没实现执行器则只记录建议 |
| 装备规划 | 大件完成、重大威胁首次确认、团队装备冲突、阶段复核 | 每名英雄下一件装备或短期候选路线 | 购买事务适配器；详见后文，不能直接替换全清单 |
| 团战准备方针 | 预计交战前、敌方关键装备揭示 | 优先威胁、保护对象、先手／反手职责、保留关键技能的策略 | 英雄本地逻辑须显式消费这些字段；危急自救仍优先 |
| 买活储备 | 中后期、基地风险上升、目标窗口接近 | 保留买活预算／允许支出 | 本地限制可花金币；买活瞬间不等待模型 |

不建议首版让 LLM 介入：每次补刀、拉仇恨、技能弹道规避、控制衔接精确时刻、临时反隐、即时买活。这些需要低延迟和高度可靠的本地实现。LLM 可决定“保留反手大招”的战略方针，但不能阻止一个明确能救命的本地施法。

### 4.1 对线规划应输出有限状态，而不是“打凶一点”

例如 `pressure` 候选至少定义：受压目标、允许参与者、最大追击区域、最低血蓝／保留蓝量、不能进入的塔威胁区、何时回到补刀。LLM 选择候选等级，具体数值由英雄／版本配置给出且有上下限。

`rotate_support` 必须考虑留下来的核心能否活、是否会漏关键经验、兵线位置、支援耗时和撤回条件。没有可用拉野执行器时，不应让 LLM 输出“去拉野”并声称它已执行。换线还需同步 assigned-lane 的实际消费点、伙伴关系与缓存失效，不能只修改一个字符串。

### 4.2 战术计划不是永远强迫五人一起走

同一团队目标可以带分工：1 号位再发育到装备节点，2／3 带 4 压塔，5 帮 1 做防守视野；或 1／3／4 打盾，2 清邻近兵线，5 控入口。应按英雄能力和到场时间选参与者，不固定“所有辅助跟核心”。

地图计划应有可预期的收益和时间窗。例如预计拆塔耗时加集结时间长于敌方核心复活窗口，则该计划应被候选生成器降权或排除。LLM 负责比较候选的战略价值，不负责凭记忆猜当前技能／物品数值。

## 5. 低频出装指挥：建议作为独立、较长周期的计划

### 5.1 现有购买流程

```text
hero_*.lua 中的 sRoleItemsBuyList[position]
  → X.sBuyList（可经过用户自定义）
  → item_purchase_generic.lua 读取
  → 复制成 bot.purchaseListInReverseOrder
  → 取末尾目标 currBuyingItemInPurchaseList
  → Item.GetBasicItems 展开组件
  → currBuyingBasicItemList / RefList / RequiredCounts
  → 库存检查、购买、运输／储藏状态检查
  → 完成后移除目标，进入下一件
```

当前处理的不只是列表：有组件计数、购买尝试记录、组件重建、自动售卖、特殊英雄和换位置／ARDM 换英雄路径。仅修改 `BotBuild.sBuyList` 不保证正在运行的购买队列随之更新。

### 5.2 模型决策边界

第一版允许四种操作：

- `keep`：继续当前路线。
- `reorder_future`：调整尚未开始购买的大件顺序。
- `replace_future`：把一个尚未投入资源的未来装备替换成白名单候选。
- `assign_team_item`：分配某件团队功能装给最合适、能及时完成的英雄；再生成对应个人未来队列变更。

第一版**不允许**模型自动出售成装、拆解装备、丢弃组件、取消已付款购买、修改玩家显式锁定出装，或购买本地不会使用的主动装备。库存、槽位、商店、配方及英雄特例仍由本地校验。

### 5.3 什么时候问模型

1. 对线信息初步清楚时建立方向，如开局后 2–3 分钟；不必因每个树枝组件请求一次。
2. 当前大件即将完成或已完成，且下个大件尚未开始投入。
3. 首次确认足以改变出装的威胁，例如明显治疗／隐身／控制问题。使用合法可见证据，未见装备不等于没有。
4. 连续几次交战暴露同类失败，并且短期伤害／控制摘要支持该判断；不凭一次死亡就整套改装。
5. 团队功能装出现重复投资或无人承担，或装备目标持有者退出／长期无法完成。
6. 每 180–300 秒做一次低频复核；事件触发与定时触发合并，通常每英雄 120 秒内不改两次路线。

战略计划可能只有效 20 秒，但装备方向可以持续数分钟或直到完成当前目标。装备响应的**申请时效**可以很短；接受后的**计划寿命**则更长。不要因通用战略 TTL 到期反复清空购买队列。

### 5.4 给模型看什么

- 英雄、position、实际战术职责、等级、当前经济和近期稳定收入估计。
- 已有装备和组件、储藏室、已确认运输中物品、槽位；观测不完整要标记 unknown。
- 当前合成目标、已投入成本、剩余成本、预估完成时间、锁定原因。
- 当前及未来 1–2 个团队目标：例如要打持久战，还是补充先手后主动抓人。
- 队友已购／正在做／承诺要做的功能装，防止重复或双方都以为对方会出。
- 敌方已知威胁和最近交战摘要，区分事实与推测。
- 合法候选：当前版本配方、剩余花费、功能、主动技能执行支持、核心路线兼容性。
- 买活储备、消耗品预算与用户锁定要求。

不依靠模型自行写物品内部名或回忆配方。候选由当前客户端数据和项目支持表生成；模型仅选择候选 ID。某件物品在商店存在，不等于 Bot 会正确使用，应另有 `active_usage_supported` 标记。

### 5.5 把装备调整实现成事务

建议新增 `build_policy`（候选与限制）和 `purchase_plan_adapter`（购买状态对接），在购买回调中经过存活／特殊英雄等前置处理后、选择新目标前应用 pending 变更。

```text
收到模型选择
→ 校验 session / team / hero / inventory_revision / build_revision
→ 重新采样库存与购买进度
→ 不满足安全边界：暂存或丢弃，不立即覆盖
→ 生成未来队列 diff，并检查组件重复、用户锁定、团队承诺
→ 原子提交队列与 build_revision
→ 由现有购买器继续执行
→ 记录实际购买和完成，更新团队装备承诺
```

最安全的第一版提交边界是：当前大件完成，尚未选取下一目标。默认锁定当前合成目标及其组件；模型仅调整剩余后缀。这样避免合成到一半来回改装。

如果以后支持中途切换，必须统一同步 `currBuyingItemInPurchaseList`、`currBuyingBasicItem`、组件列表、参考列表、计数、重建计时器、购买尝试以及 `SetNextItemPurchaseValue` 等状态，不能只清空一个变量。新路线应使用真实剩余组件计算，不重复分解虚拟 outfit 导致重买出门装。

当前 `_countOwnedEverywhere` 注释明确表示不能可靠检查信使包。因此运输状态不确定时，应延迟涉及重购／替换的调整，而不是把未观测物品当作不存在。用购买日志、交付确认与保守保留解决这个缺口后，才扩大权限。

自动售卖也必须联动：未来路线变化后重新检查原 `sSellList` 与通用售卖规则，防止旧规则卖掉新计划依赖的组件。已完成的购买无法通过恢复数组撤销；回退只恢复未来决策，不虚构金币退款。

### 5.6 输出示例

以下候选 ID 仅示意，不代表当前仓库已有实现。身份和版本由网关绑定，具体物品和分工由候选表展开。

```json
{
  "kind": "build_plan",
  "schema_version": 1,
  "session_id": "match-001",
  "team_id": 2,
  "player_id": 3,
  "based_on_build_revision": 7,
  "based_on_inventory_revision": 42,
  "operation": "replace_future",
  "candidate_id": "support_survival_then_team_utility",
  "apply_at": "after_current_item_complete",
  "reason_code": "team_survival_gap",
  "proposal_expires_game_time": 940
}
```

示例意图：辅助先完成正在合成的装备，再把未开始的贪输出选项换成当前允许的保人路线。模型不负责在战斗中选择微光目标；那仍由现有物品使用逻辑执行。

团队功能装承诺需有 owner、预计完成时间、复核期限和状态（proposed／accepted／building／completed／cancelled）。玩家退出或路线被本地拒绝时撤销承诺，避免大家永久等待一件实际没人做的装备。重复功能装也不是绝对禁止，而是带团队覆盖与到场区域判断。

## 6. 避免多个 LLM 建议互相打架

建议一个队伍级规划入口，但维护不同生命周期的计划：

| 计划 | 起始寿命建议 | 失效条件 |
|---|---|---|
| 对线方针 | 30–90 秒 | 对手换线、核心状态恶化、塔消失、兵线条件不成立 |
| 地图／推进计划 | 15–45 秒 | 关键参战者死亡、目标消失、基地威胁、过期 |
| 装备方向 | 当前大件结束后延续到下一复核点 | 威胁证据改变、库存／角色改变、用户覆盖 |
| 团队装备承诺 | 到完成／明确撤销，定期检查进度 | 持有者退出、无进度超时、路线变更 |
| 买活储备 | 阶段性策略 | 阶段／风险变化；实际买活判断仍即时执行 |

仲裁顺序建议：行为合法性与危急自救 → 用户锁定 → 已付款／已承诺的经济状态 → 当前可行的团队计划 → 个人策略偏好。战略想打架但关键装备未成时，候选生成器应提供“等待装备”选项；模型不能一边要求立即开战，一边让所有关键英雄去偏远商店。

同一请求可复核多个 dirty 领域，但使用不同字段与版本；装备响应迟到不应覆盖更新的地图目标，地图计划到期也不撤销装备方向。可以配置不同模型 profile，但第一版建议共用队伍输入与规则校验，先降低复杂度。

自定义配置可在总体方案上增加 `domains.laning`、`domains.objectives`、`domains.items` 的 enabled／shadow／apply 开关和频率；出装额外提供 `lock_current_item=true`、`allow_sell=false`、`respect_user_build=true`、候选白名单。模型地址、模型名和 generation 参数继续由网关统一管理。

## 7. 推荐优先落地顺序

1. **日志＋规则候选**：先能解释当前 desire、最终动作、对线让资源和购买状态，建立不接模型的基线。
2. **低频出装影子模式＋团队目标影子模式**：比较原路线与模型建议，发现错误物品／不可执行建议，验证成本与时效。
3. **只调整未来装备＋推塔／防守候选**：这些边界较清楚，容易做事务检查和对照。
4. **Roshan、地图资源与辅助轮转**：补齐观测可信度、伙伴关系与跨模式目标消费。
5. **对线压制／换线、视野与开雾、团战方针**：先实现执行器，再让模型选择，不用自然语言输出代替功能。

验收除了胜率，还应检查：下一件装备完成时间、重复／无效购买、组件闲置成本、团队功能装重复率、核心关键装备延迟、辅助离线造成的核心死亡、团战后的目标转化。对照组要包含“原版”“相同候选的规则规划器”“规则规划器＋LLM”，否则无法判断提升来自模型还是新增工程逻辑。
