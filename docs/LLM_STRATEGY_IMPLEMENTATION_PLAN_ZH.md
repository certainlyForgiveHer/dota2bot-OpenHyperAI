## 2. 成功定义与范围边界

目标：在保留现有操作机制的条件下，改善团队目标协调、个人地图风险判断和低频经济规划。

三种成功不得混淆：

1. **集成成功**：异步请求、有效响应、计划被消费、失败时原规则继续。
2. **行为兼容**：不开功能时保持基线；开功能后没有新增动作抢占、重复购买或明显操作退化。
3. **决策收益**：对照实验支持被抓减少、目标转化改善等，且没有不可接受的发育／胜率损失。

最终报告必须分别给结论。仅通过前两项时可以发布实验能力，但不能宣称“Bot 更强”。

### 2.1 保护清单

MVP 不修改英雄 `SkillsComplement/Consider*`、补刀／反补算法、局部攻击目标选择、技能时机、模式 `Think` 的移动／攻击算法和 MinionThink；不新增 `bot_generic.lua` 英雄级 Think 接管引擎。

新增战略模块禁止直接调用 `Action_*`、`ActionQueue_*`、`ActionPush_*`、`Action_ClearActions` 或设置即时攻击目标。不得通过 monkey patch 替换这些 API，不得让模型输出代码执行。

允许的生产接点限于：已经审核的正常宏观评分分支、经验证的团队意愿接口、购买器的未来清单提交边界，以及必要的只读采样／缓存维护入口。TS 生成文件由源文件构建产生。

“保留微操”是保留算法与控制权，不承诺启用战略后每个动作轨迹不变；模式或活动区域改变会间接改变遇敌和施法机会。

**“技能时机”的范围定义（2026-09-21 决策）**：保护清单中的“技能时机”指英雄 `Consider*` 函数内部的施法时机判断——是否施放、何时施放、对谁施放，含 `X.SkillsComplement()` 的顺序优先规则。**不含物品使用时机**：物品使用由 `ability_item_usage_generic.lua` 的 `X.ConsiderItemDesire` 分派子系统独立决定，属 2.3 的新增接点。

为避免以词义解释代替实质保护，物品层的策略门槛必须同时满足三重行为约束，并作为 G3 验收项：

| 约束 | 内容 | 验证 |
|---|---|---|
| 单调性 | `final_desire ≤ base_desire`，只能降低，永不提升 | 日志断言；出现 `final > base` 即失败 |
| 只延不创 | 只能推迟 `ConsiderItemDesire` 已决定使用的物品，不得发起新使用 | 新增物品使用次数 ≤ 基线 |
| 有界延迟 | 单件物品被抑制不得超过配置上限；保命类物品且 HP 低于阈值时抑制失效 | 新指标“被抑制超时次数 = 0” |

最坏情况因此被限定为“某件物品被推迟了有界时间”，而不是“bot 停用或乱用物品”；`off` 时仍须原样返回。

### 2.2 第一版不承诺的能力

不承诺任意精确集结点、指定谁 A 哪个英雄、完整换线、自动拉野堆野、复杂开雾路线、自动卖／拆装备、即时买活由模型决策、**调整买活储备**。没有执行器的建议只能记录，不能标记为已执行。

**买活储备维持现状（2026-09-21 决策）**：现有储备机制（`item_purchase_generic.lua:272-283`，见 §3）原样保留，MVP 不接受模型对储备线或储备窗口的任何调整。这是**暂缓而非否决**——更合理的改法尚未确定，待有具体方案后再单独立项。当前唯一必须生效的是：储备会通过抬高 `cost` 拒绝购买，因此出装候选的生成必须预先扣除储备，避免模型收到一个会被储备静默拦下的候选（见 §8）。

队伍偏好属于软影响：个人安全判断可以不接受。若现有逻辑无法让成员集结，标记“现有执行器覆盖不足”，另立后续任务，不偷偷扩大微操改动范围。

### 2.3 团战准备方针的优先与落地边界

**决策（2026-09-21）**：ROLE 文档 §4 的“团战准备方针”提升为优先介入点。理由是该点最贴合 LLM 的适用边界——英雄本地逻辑的判断半径受限于邻近单位，**结构上无法表达**“保留本技能以配合地图另一侧队友”这类跨时间、跨英雄的权衡。以斧王为例，`hero_axe.lua:151-205` 的全部输入是 `J.GetProperTarget(bot)`、`GetNearbyHeroes(bot, 1600, …)`、`GetAlliesNearLoc(bot:GetLocation(), 1600)`，且施法为顺序优先规则（`ConsiderR → ConsiderQ → ConsiderW`，首个 desire > 0 即执行并返回）。

**首版范围收窄为物品层（方案 A1），不修改任何英雄文件**：

| 项 | 内容 |
|---|---|
| 接点 | `bots/ability_item_usage_generic.lua:997-1025` 的物品分派循环 |
| 依据 | `X.ConsiderItemDesire`（同文件 `local X = {}`，1129 行起注册）覆盖 167 个物品；**实测 0 个英雄文件覆盖该表**；唯一执行出口为第 1019 行 `X.SetUseItem` |
| 侵入面 | 1 个通用文件的 1 个循环；不触及 `SkillsComplement`／`Consider*`、不 monkey patch、不调用动作 API |

该接点不在 2.1 末段枚举的清单内，按 4.1 要求**须单独提交设计变更记录**，说明消费字段、失败返回与相对位置，并须满足 2.1 定义的三重行为约束（单调性、只延不创、有界延迟）。

**技能层不在首版范围**：`X.SkillsComplement` 是逐英雄手写的顺序优先规则，要施加保留策略只能在 128 个英雄文件中逐个加守卫，与 2.1 直接冲突。若物品层影子数据证明该介入点确有价值，再单独立项讨论是否对 6.2 的试点英雄开放“纯否决守卫”（在既有 `Consider*` 之前插入、不改变优先级顺序、不新增施法），届时须先修订 2.1。

**前置触发要求**：本介入点依赖**开战前**方针已就位。当前预算为常规间隔 25 秒、请求 deadline 4 秒、计划 TTL 20–30 秒，而一场团战可能在该 TTL 内打完，因此触发必须是领先指标（敌方关键装备首次确认、双方开始集结、Roshan 时间窗），不能以“团战开始”为触发，否则方针到达时战斗已结束。

## 4. 拟实现结构与文件边界

以下路径为拟新增，不是已存在的功能。

```text
普通 Bot / 可选 FretBots 事件
  → 合法观测与事件
  → 本地个人风险状态（立即生效，不等待模型）
  → 网关：队伍聚合、去重、预算、provider adapter
  → LLM 从合法候选中选择
  → 协议校验、版本检查、本地复核
  → team / personal / build 三类计划缓存
  → 小范围评分接点 / 未来购买队列接点
  → 原有操作执行器
```

| 拟新增模块 | 位置 | 职责 |
|---|---|---|
| contracts | `typescript/bots/FunLib/strategy/contracts.ts` | 观测、事件、候选、计划类型；无引擎动作 |
| observation / events | 同目录 | 只读快照、差分、阶段触发、团战聚合 |
| personal_risk | 同目录 | 每 Bot 的证据／风险状态机与角色配置 |
| state / client | 同目录 | session、版本、缓存、异步传输、在途请求和过期 |
| policy | 同目录 | 受限评分策略、原规则回退；不额外调用模式 GetDesire |
| build_policy | 同目录 | 装备候选、用户锁定和团队功能装承诺 |
| 配置 | `typescript/bots/Customize/strategy.ts` | 开关、域、阈值、网关地址；不含模型密钥 |
| 网关 | `services/strategy-gateway/` | 独立 Node/TS 包，配置、队伍聚合、provider、日志、预算 |
| 协议与测试 | `services/strategy-gateway/schemas/`、`tests/strategy/` | JSON Schema、固定输入、故障注入、Lua 生成物验证 |

## 5. 策略和请求契约

### 5.1 数据字段

观测：`schema_version, session_id, team_id, bot_id, role, game_time, observed_at, visibility, source, state_revision`，加己方状态、敌方最后可见、兵线、建筑、资源和当前计划。未知写 unknown/null，不写 0。

事件：`event_id, kind, subject_id, first_seen, last_seen, evidence_ids, confidence_class`。事件置信度来自证据规则，不用模型自评概率代替。

计划公共字段：`domain, request_id, request_generation, based_on_revision, plan_version, candidate_id, expires_game_time, reason_code`；身份字段由网关绑定并复核。team、personal、build 各有独立版本与寿命。

候选必须带执行能力标签。模型只能选择当前提供的 ID 或 `no_change`；不能发任意坐标、物品名、API 名称或程序片段。输入和输出用 Schema 校验并限制大小。

### 5.2 模式与生命周期

- `off`：不请求模型、不改变评分／队列；行为接点返回原值。默认值。
- `shadow`：采样、规划、记录建议；风险和 LLM 建议均不改变行为。
- `apply`：只对显式开启的 domain／试点 Bot 应用策略；本地风险规则和 LLM 分开开关以便消融。

请求：idle → pending → received/rejected/timeout；最多一个队伍级在途规划请求，后续变化合并成 dirty 最新状态。每个 Bot 有独立 trigger 状态，但调用由网关合并，避免同一失踪信息触发五次模型请求。

响应到达只更新缓存。应用前检查 session／team／Bot、请求代数、年龄及关键证据是否仍成立；不因无关采样 revision 增长而一律丢弃。超时／断网／非法结果保留仍有效计划，否则用原规则。暂停时网络超时用单调真实时间，行动有效期用游戏时间；恢复时重验。

### 5.3 自定义提供商配置

必须支持 adapter、base_url、model、api_key_env、timeout、generation 参数和显式白名单 extra_body；provider 不支持的参数启动时报错。密钥在网关环境变量中，不写 Lua、不进入版本库或审计日志。

至少验证两种配置：确定性 fake provider 和用户配置的真实服务；实际地址／模型未知不阻碍本地实现，但真实联网验收必须记录配置摘要和结果。MVP 不承诺任意 API 协议“只换 URL 就能用”。

初始预算：单队 1 个模型在途请求、常规间隔 25 秒、4 秒请求 deadline、常规计划 20–30 秒 TTL；单队单局 120 次／150,000 总 token 上限，任一达到即暂停模型调用。事件可以立即撤销危险旧计划，但不绕过全局预算。

响应正文上限初定 32 KiB，结构化快照目标上限 64 KiB；超限拒绝／按字段优先级裁剪，不阻塞游戏线程。所有值可配置并写入 run manifest。

## 6. 事件与个人读图规格

### 6.1 团队事件

| 事件 ID | 检测与去重 | 验收重点 |
|---|---|---|
| E01 阶段节点 | previous < 300/600/1200 <= current；session＋阈值去重 | 不用浮点相等；重载不连发；新 session 重置 |
| E02 死亡／复活 | 原生事件或存活差分；英雄身份去重 | 克隆／幻象不冒充英雄死亡；连续死亡合并 |
| E03 建筑变化 | 建筑身份＋状态变化；反补也记建筑消失 | 阵营、路线、级别正确；首次快照不制造历史事件 |
| E04 团战结束 | 区域聚类＋双方参战＋伤害／死亡；脱战窗口。**首选证据源：`dota_combatlog` 已在 `bots/FretBots/OnEntityKilled.lua:211` 注册，但处理器 `OnCombatlog`（78-81 行）尚为空壳**，接入成本低于轮询差分 | favorable/unfavorable/mixed/uncertain；不把跨图击杀合并 |
| E05 Roshan | 已验证回调或击杀时间变化 | 死亡不自动推出击杀方或盾持有者 |
| E06 不朽盾 | 合法物品／状态观测 | 获取、消耗、到期、失去视野分开；敌方未知保留未知 |

事件初始化从快照建立基线，不把已有死亡塔全部回放为新事件；热重载用 session checkpoint 恢复。无法可靠关联 session 时显式新建并记录 resync，不假装完美去重。

### 6.2 每 Bot 的触发器

初始集合：深入兵线与敌人失踪、附近伙伴离开、资源区失守、关键装备完成、己方被连续击杀、团队目标变化，以及**敌方关键装备首次确认（团战准备方针的领先触发，见 2.3）**。角色仅改变观察权重与候选，不改英雄身份或选人。

首个场景 RISK01：核心位于深入兵线区域，敌塔附近可见且持续无人接线，并存在失踪敌人／缺乏支援等证据。状态为 normal → watch → caution → recovery；进入与退出阈值不同。

- 初始采样 0.5–1 秒；常规证据持续 2–3 秒才升级，明确新增敌人威胁不等待该窗口。
- 敌人最后可见位置与失踪时间只估计“可能到达”，不宣称已在那里。
- 敌人明确出现在另一侧、附近友军保护等是风险降低证据。
- 本地状态立即更新；启用风险 apply 时，只压低已审核的继续深入倾向，不强制清动作。
- LLM 低频选择继续施压、降低推进承诺、转为既有可执行发育候选、等待支援或 no_change。
- 没有可验证安全转区执行能力时，只允许降推进倾向，不把“转安全区”标为已完成。

| Role | 第一轮触发重点 | 第一版允许影响 |
|---|---|---|
| 1 | 深线、失踪、支援减少、装备窗口 | 推进承诺、已有正常发育分支偏好 |
| 2 | 清线后机会、中塔压力、己方能力窗口 | 现有路线／宏观目标偏好；不承诺新游走执行器 |
| 3 | 到场人数、配合能力、目标窗口 | 推进意愿及是否等待团队条件 |
| 4 | 支援需求、核心暴露、团队目标 | 已有防守／推进模式偏好 |
| 5 | 1 号位暴露、伙伴状态、目标覆盖 | 已有保护相关宏观候选；新视野执行器后续再做 |

样本至少覆盖 1–5 号位各一个适配组合；不从五个样本宣称覆盖全部英雄。非试点英雄保持 off 或 shadow。

## 7. 评分介入规则

原逻辑硬性提前返回 → 正常基础评分 → 有限策略偏好 → 原本的血量／风险 cap → 引擎模式仲裁。

**初版首站为防守域，不是推塔域（2026-09-21 决策）**：防守的团队意愿通道已验证可用（见 §3），推塔通道结构上不通，因此 T08 先在既有防守基线适配，零新增代码即可验证“网关 → 计划 → 消费”整条链路是否真正跑通。

推塔域留待其后单独评估。若届时仍需启用，可仿 `J.GetDefendLaneDesire`（`jmz_func.lua:3344`）补一个对称的合流点——属新增接点，须提交设计变更记录。推塔域启用时优先尝试“保留目标路评分，小幅降低其他路正常推进评分”。只有实验表明影响过弱，才开放目标路有限增益，并且不能越过原风险 cap。未知原因的低分／0 分不得被抬升。

个人 risk 的否决优先于团队软偏好；本地紧急逻辑始终最高。不能把团队“推中”解释为必须五人一起冲。

不全局 clamp 所有原返回值：已有路径可能使用超常数值或非数值 fallback，不能为接 LLM 顺手改变语义。只规范新增策略参数，在明确数值正常路径应用。off／shadow 必须原样返回。

每次应用记录 `base_desire, final_desire, original_cap, domain, plan_version, reason_code, eligibility`。日志只读取本次已算结果，不再次调用 GetDesire；限频并在有变化时记录，避免逐帧海量输出。

## 8. 出装事务边界

首版操作仅 keep、reorder_future、replace_future、assign_team_item；锁定当前合成目标、已付款组件和用户显式配置。不能通过新路线触发自动卖成装／丢组件。

提交条件：当前目标完成、下一目标尚未展开，inventory/build revision 和角色／英雄身份仍匹配。深拷贝未来后缀，先生成 diff 并验证，再一次性替换运行队列；不得原地污染英雄模板共享表。

候选来自当前配方、库存、项目主动装备支持表和团队功能需求；不让模型凭记忆生成配方。信使物品无法可靠观测时保守等待。联查旧 sell list，避免新路线依赖被旧售卖条件误删。

每项事务记录前后 future queue、锁定 current target、组件／运输已知状态、候选 ID、校验结果、实际购买与完成。失败不提交；已经花掉的金币不能靠恢复数组“回滚”。关功能后保留已承诺的当前合成，未来路线在下一安全边界恢复兼容的基线。

团队装备承诺包含 owner、状态、预计完成窗口和复核时间；退出／取消时释放。默认 180–300 秒复核，重大威胁或大件完成可提前标记 dirty；不为每个组件请求模型。

**买活储备与出装的边界（2026-09-21 决策）**：购买器已有买活储备机制（见 §3），它通过抬高 `cost` 使购买更保守；而 `reorder_future`／`replace_future` 调整的是同一笔金币预算。**储备本身在 MVP 维持现状、不受模型调整**（见 §2.2），但两者仍会在同一预算上相遇，因此必须做到两点：

1. **候选生成预先扣除储备**：提供给模型的物品候选与剩余花费必须已经扣掉储备线，使模型永远不会收到一个会被储备静默拦下的候选。否则模型会以为计划已被接受，而实际购买一直被拒。
2. **被储备拦下必须留痕**：已接受的出装计划若被储备阻止执行，记入事务日志并标注 `blocked_by_buyback_reserve`，不得静默丢弃。

此条补充 ROLE 文档 §6 的仲裁顺序——原顺序（行为合法性 → 用户锁定 → 已付款／已承诺经济 → 团队计划 → 个人偏好）未覆盖“经济储备 vs 出装”，而 T10 会实际改动同一预算，故须在 T10 开工前生效。

### 阶段门的可判定标准

- **G0 能力成立**：确认 HTTP callback 形态、可达地址、延迟期间 Bot 行动继续；确认团队接口实际传播路径或选择替代；重开／暂停／死亡／scope 行为有记录。未测即未通过。
- **G1 可追溯**：所有协议 fixture 与事件差分测试通过；未知信息表示正确；输入→事件→请求→响应→校验可关联；shadow 无策略动作或评分／队列写入。
- **G2 可控**：非法／超时／乱序／过期／错队响应全部拒绝；预算和去重生效；RISK01 正反例通过；接入真实 provider 后记录延迟和参数兼容性。
- **G3 不侵入**：off/shadow 在相同 stub 输入下原评分、队列和新增动作数完全一致；保护文件无行为改动；风险 cap 不被突破；游戏中无新增停滞、施法被新层清断等故障。战绩仍未证明。
- **G4 经济正确**：所有事务用例通过；试点无新增重复组件、错误出售、库存不一致提交；实际购买与计划一一对账；关功能恢复不浪费已购组件。
- **G5 覆盖完整**：U03 所列事件全有实现与正／负／unknown 测试；五个位置试点有记录；不支持项明确列出，不能称全部角色已完备。
- **G6 可交付**：手册、配置样例、审计包、关闭演练齐全；实验结果独立说明技术完成和效果证据。若效果不确定，仅维持实验性开关，不默认开启。

## 10. 测试与实验协议

### 10.1 离线与故障测试

必须用例：阶段跨阈值、初始化无历史事件、相同事件多人上报、跨图战斗分离、敌方未见状态、死亡期间回调、暂停恢复、重开局、迟到／乱序、非法 JSON、超限正文、错误队伍、失效候选、429、断网、预算耗尽、组件运输不确定、出装响应后英雄／role 改变。

风险 fixture 至少包括：深线＋多人失踪、深线但敌人明确在另一侧、塔区无视野、友军保护、证据短暂闪断、风险解除。验收是状态和理由符合预先定义，不要求模型措辞固定。

使用 fake provider 和注入时钟做确定性测试；随机模型不参与单元测试判定。记录真实响应并回放，可复现校验／消费，但不保证再次联网生成完全相同文本。

构建检查：新增逻辑类型／纯逻辑测试、TSTL 编译、Lua 语法和导入路径、目标环境 smoke test；纯 TS 通过不能代替 Lua 运行。生成文件检查不得顺手全库 prettier／release，避免不相关变更。

### 10.2 性能预算

初始目标：新增本地读缓存／策略路径 p95 < 1 ms／次；较重状态采样单独限频；同环境匹配对局的帧时间 p95 退化目标不超过 5%。P0 先验证测量能力与噪声，再冻结阈值；测不到就报告未测，不能填通过。

记录网络／provider／解析／本地应用各段延迟。网络等待较长允许丢弃计划，不允许阻塞行动；模型延迟目标不是运行安全保证。

### 10.3 对局分组与成功指标

A 原版；B 相同观测／候选＋确定性规则（无 LLM）；C B＋LLM。C 内分团队策略、个人策略、装备开关，必要时做单域消融，避免一次全开后无法归因。

固定客户端、脚本版本、英雄／role、难度和 FretBots 增益，交换阵营；同一随机 seed 只在可支持时记录，不宣称引擎完全确定。先做每组 10 对交换阵营的配对试验用于发现问题和估计方差，不当作充分胜率证据；后续样本量按先验最小效果与试验方差确定，冻结方案后再扩大。

预登记指标：

- 个人读图：每 10 分钟深入危险区域内死亡次数、危险暴露时长、有效风险触发率；同时看补刀、经验和经济，避免以挂机换安全。
- 团队战略：团战结束后 30／60 秒目标转化率、计划接受／拒绝／完成比例、模式抖动和无效行走。
- 装备：关键装备时间、闲置组件价值、重复功能投入、重复／错误购买、购买事务拒绝原因。
- 整体：胜率区间、时长、Lua 错误、帧时间、请求／token／费用、迟到和非法响应率。

危险区定义、团战窗口与“目标转化”的分母在实验前写进 manifest；不能在看到结果后改口径。胜率和安全指标需同时看经济代价；报告差异、区间、样本量和未解决的混杂因素。

## 11. 审计记录与回退

### 11.1 单次运行证据包

建议 `artifacts/strategy/<run_id>/`，默认排除出 Git，脱敏小型 fixture 才纳入版本库：

```text
manifest.json              commit、客户端、场景、配置哈希、provider/model 摘要
capabilities.json          每个探针的结果／限制
observations.jsonl         合法快照或其归档引用
strategic-events.jsonl     事件、证据、角色风险变化
requests.jsonl             请求 ID、输入引用、模型与参数摘要、耗时／token
plans.jsonl                响应引用、校验、拒绝、版本、有效期
applications.jsonl         原评分／最终评分、计划消费、购买事务
metrics.json               预登记口径与结果
validation.md              阶段门结果、问题、结论、关闭演练
```

单条评分变更必须能追溯：run → observation → event → request → response → accepted plan → score／purchase application → outcome。拒绝和 no_change 也记原因。记录模型结构化 reason_code，不要求或存储隐藏推理过程。

禁止记录 API key、Authorization、玩家账号；聊天不作为战略输入。响应／快照按大小与留存期限配置管理。日志队列有上限，丢记录必须计数；审计链缺失的运行不能判定为验收通过，但游戏继续原规则，不因写日志阻塞。

### 11.2 回退触发

跨队信息污染、策略层发出动作、突破安全 cap、陈旧计划执行、重复购买／错误出售、可复现停滞任一出现：禁用对应 apply 域并保存证据。协议／网关级问题关闭全部模型 apply。不得靠提高经济／经验奖励掩盖问题。

正常关闭：清除战略与个人偏置，下一次正常评分返回基线；不清动作队列。购买按第 8 节在安全边界恢复，保留已付款状态。需要代码级回退时回退独立功能变更，不覆盖既有用户修改。

对未知能力、失败和未测项使用 pass/fail/not_run/unsupported，不使用模糊的“基本通过”。

## 14. 附录：ROLE §4 十二个介入点的 MVP 可实现度

**本附录是分析者评估，不是已确认结论**，须由 T03 接点映射复核后修正。评估依据为计划自身的约束（§2.1 保护清单、§2.2 不承诺清单、§4.1 允许接点）与当前源码实测。

| # | 介入点 | MVP 可实现度 | 卡点 |
|---|---|---|---|
| 1 | 开局分工 | ❌ 仅记录 | 分路只有读取：`GetAssignedLane()` 共 44 处调用，引擎类型声明（`ts_libs/dota/interfaces.ts:153`）也只提供 getter，全仓库不存在任何写分路的 API；§2.2「完整换线」不承诺 |
| 2 | 对线方针 | ⚠️ 部分 | `rotate_support`／`swap_lane` 无执行器；§4.1 要求无拉野执行器时不得输出「去拉野」 |
| 3 | 辅助离线／支援 | ❌ 需新执行器 | 需新建「4／5 号位任务适配」 |
| 4 | 地图资源分配 | ⚠️ 部分 | farm 区域分配无执行器，只允许既有正常发育分支的偏好 |
| 5 | 团战后转化 | ✅ | 复用既有 push／roshan／farm 模式偏置 |
| 6 | 推进与高地 | ⚠️ 通道受阻 | 推塔团队意愿通道结构上不通（§3）；只能走 `aba_push.ts` 自有评分 |
| 7 | 防守与资源交换 | ✅ 但受限 | 防守通道已验证可用；但「只在非危急路径，不能削弱基地保护」 |
| 8 | Roshan／盾节奏 | ✅（P5） | §4.1「先保留所有人数／输出／安全条件」 |
| 9 | 视野与开雾 | ❌ 仅记录 | ROLE §4 原文「没实现执行器则只记录建议」 |
| 10 | 装备规划 | ✅ | T09／T10，事务边界最清楚 |
| 11 | 团战准备方针 | ✅ 物品层／❌ 技能层 | 见 §2.3；技能层需改动英雄文件，待单独立项 |
| 12 | 买活储备 | ❌ 不纳入 MVP | 机制原样保留、不受模型调整（§2.2）；改法未定，属暂缓而非否决，待单独立项 |

合计：**可落地 4 项**（团战后转化、防守、Roshan、装备规划）、**部分 3 项**（对线方针、地图资源分配、推进与高地）、**仅记录、需新执行器或暂不纳入 5 项**（开局分工、辅助轮转、视野开雾、团战准备方针技能层、买活储备）。

需要正视的一点：最有 LLM 独特价值的几项——对线方针、辅助轮转、视野开雾、团战准备方针的技能层——恰好集中在受限或仅记录那一类，因为它们的价值来自跨时间跨英雄的权衡，而执行它们需要新执行器，新建执行器又撞上 §2.1 的微操保护。这不是实现顺序问题，而是当前约束下的能力上界，应写入对外说明，避免以 12 点表承诺过高的能力预期。
